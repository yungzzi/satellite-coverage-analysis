# SIRIAgent 后端部署白话说明

> 目的：用非专业语言说明“卫星覆盖/选星引擎”接入 SIRIAgent 时，网页、后端、计算服务和部署位置分别做什么。
> 本文只解释部署方案，不改变现有覆盖引擎，也不代表“只保留复杂引擎”已拍板。

## 一句话全景

可以把系统想成餐厅：SIRIAgent 网页是前台，平台后端是服务员，卫星覆盖/选星引擎是后厨。

```text
用户聊天
  → SIRIAgent 网页（Vercel 托管）
  → 平台 Flask 后端：识别需求、追问参数、转发请求
  → 独立计算服务：运行 SGP4、覆盖窗口和选星计算
  → 返回窗口、统计和推荐卫星
  → 网页展示
```

目前本工程已有“后厨的计算发动机”，即 Python 覆盖和选星函数；还没有独立 FastAPI 服务，也没有把计算服务正式部署到云端。

## 云端是谁提供的？研究院是否要出一台电脑？

当前 SIRIAgent 网页及其轻量后端部署在 **Vercel**。Vercel 是第三方云托管平台：物理服务器由 Vercel 提供和维护，研究院不需要在办公室摆一台电脑来运行网页。

但接入卫星重计算后，仍必须有一处长期运行计算服务的地方；不能凭空完成计算。通常有三种选择：

| 选择 | 真正运行计算的地方 | 是否需要研究院提供物理电脑 |
| --- | --- | --- |
| 研究院已有服务器或虚拟机 | 研究院机房/校内云 | 通常不需新买电脑，但需管理员提供运行环境 |
| 租用第三方云主机 | 阿里云、腾讯云等云厂商的虚拟服务器 | 不需研究院自有物理电脑，但需研究院负责账号、经费、安全和数据规则 |
| 用户自己的电脑 | 本机 | 只适合开发和临时演示，不能作为正式服务 |

所以，研究院**不一定需要拿出一台新的实体电脑**；但必须决定由谁提供一台可长期运行的“服务器/云主机”。Vercel 可以继续负责前台与轻量转发，重计算另放在该服务器上。

## Flask、FastAPI、Vercel 分别是什么？

- **Flask**：Python 的轻量 Web 后端框架。平台现有 Flask 后端负责接收网页请求、选择 skill、追问缺失参数、转发结果。
- **FastAPI**：也是 Python Web 后端框架。它适合把现有 Python 函数包装成清晰的接口，例如 `POST /v1/coverage-selection`；它会帮助校验输入格式，并可自动生成接口说明页。
- **Vercel**：第三方云部署平台。它适合网页、聊天和短小请求；但对运行时长、内存、本地文件等有约束，不应承担数百颗卫星的重计算。

Flask 与 FastAPI 本质上都是“让别的程序通过网络调用 Python 函数的接线板”。FastAPI 并不会让轨道算法本身神奇变快；性能仍主要由 SGP4、几何计算、卫星数量和时间范围决定。

本项目建议“平台继续 Flask，计算服务采用 FastAPI”，是职责分工，而不是 Flask 不能做。若研发同学有统一的 Flask 服务规范，也可以按其规范实现独立计算服务。

## Docker 是什么？

Docker 可以看作标准集装箱。程序运行不仅需要 `.py` 文件，还需要指定版本的 Python、`sgp4`、`skyfield`、`numpy` 等依赖和启动命令。Docker 将这些一起装进一个可重复运行的容器：

```text
Docker 容器
├─ 覆盖/选星 Python 代码
├─ Python 与第三方依赖
├─ FastAPI 接口程序
└─ 启动配置
```

这样在测试机、研究院服务器或云主机上，运行环境更一致。Docker 不是算法本身，也不是云服务器；它是把程序可靠搬运和运行的一种方式。

### 用未来的代码示意 Docker 在做什么

下面是将来可能出现的 `Dockerfile`，**只是教学示意，当前项目尚未创建它，也不能直接运行**：

```dockerfile
# 1. 选择一个自带 Linux 与 Python 的基础箱子
FROM python:3.11-slim

# 2. 之后的命令都在箱子里的 /app 目录执行
WORKDIR /app

# 3. 先复制依赖清单，再安装 sgp4、skyfield、numpy 等库
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# 4. 再复制本工程的代码
COPY src ./src
COPY service ./service

# 5. 容器启动后，运行 FastAPI；8000 是服务端口
CMD ["uvicorn", "service.app:app", "--host", "0.0.0.0", "--port", "8000"]
```

逐句看：`FROM` 是先拿一个干净的 Linux+Python 空箱；`COPY` 是把项目文件搬进箱子；`RUN` 是在箱子里安装依赖；`CMD` 是箱子启动后自动执行的命令。`service/app.py` 是未来才会编写的接口程序，它会调用现有的 `analyze_collection_pipeline(...)` 与 `run_selection(...)`，而不是重写轨道算法。

在开发者电脑或服务器上，大致会执行：

```powershell
# 把 Dockerfile 变成一个名为 satellite-service 的镜像（可运行的箱子模板）
docker build -t satellite-service .

# 从模板启动一个容器，把服务器的 8000 端口转给箱子里的 8000 端口
docker run -p 8000:8000 satellite-service
```

此时访问服务器的 `http://服务器地址:8000`，请求会进入容器里的 FastAPI。正式环境还会增加 HTTPS、令牌鉴权和 TLE 缓存持久目录；不会直接把这个教学命令暴露到公网。

## 服务器通常是 Linux 吗？会不会造成困难？

是的，绝大多数云服务器和研究院服务器使用 Linux（常见为 Ubuntu、Debian、CentOS/Rocky Linux）。原因是它适合长期运行、成本低、远程管理和 Docker 生态成熟。也可以使用 Windows Server，但通常不作为 Python/Docker 服务的首选。

这不会要求你先学会 Linux 才能推进：Docker 的价值之一正是让开发者在 Windows 上构建和测试，再把相同容器交给 Linux 服务器运行。不过正式部署前仍要做一次 Linux 冒烟验证，重点检查：

- 代码中不能写死 Windows 路径、`.bat` 命令或盘符；
- TLE 缓存需要配置到容器外的持久目录；
- 本项目的自研 Python 覆盖引擎适合跨平台部署；
- 可选 ATK 引擎依赖 Windows/本机 ATK，不应作为第一版 Linux 容器服务的必选能力。

因此第一版服务建议保持“自研引擎 + 复杂传感器 Profile”的范围；这只是部署边界，不改变现有引擎的保留策略。

## 后端是否需要数据库？

最小 demo **不必先上数据库**。请求到达后，同步计算并把结果直接返回即可；现有 TLE 缓存和配置文件可先放在服务机器的持久磁盘。

正式使用时，数据库或其他持久化存储可能用于：

- 保存任务状态、历史结果和错误日志；
- 保存用户提交的长任务及其结果链接；
- 记录所用 TLE 版本，保证结果可复现；
- 管理卫星传感器 Profile、权限和调用审计。

数据库通常可部署在研究院服务器上，也可使用第三方托管数据库；大文件或结果表通常适合放对象存储/文件存储。无论采用哪种，都不能依赖 Vercel 临时运行环境的本地磁盘做长期保存。

### 数据库究竟放在 Vercel 还是研究院服务器？

两者都不是自动答案，取决于研发的现有规范：

- **最小 demo**：不用数据库，结果直接返回；TLE 缓存放计算服务机器的持久磁盘。
- **小规模正式版**：数据库可以与计算服务一起部署在研究院服务器/云主机上，管理简单但两者共用一台机器。
- **规范正式版**：研究院已有数据库则优先接入；否则可由研究院账号使用第三方托管数据库。计算服务和数据库可分别部署。

Vercel 的临时函数文件系统不能当数据库使用。即使平台已有连接到 Vercel 的数据库，也必须先由平台研发确认是否允许新增卫星任务数据、保存期限和访问权限。

### 数据库可以只是一个文件吗？

可以。**SQLite** 就是一种完整的关系型数据库，但它保存在一个文件中，例如 `data/service.db`。程序仍可像使用普通数据库一样查询、筛选、更新数据；区别是它不需要另起一个数据库服务器进程。

| 方式 | 例子 | 适合什么情况 |
| --- | --- | --- |
| 普通文件 | CSV、JSON、TOML、TLE 文本 | 配置、卫星目录、TLE 缓存；结构简单且主要读入 |
| 文件型数据库 | SQLite 的 `.db` 文件 | 单台计算服务、小规模任务/日志/传感器 Profile；便于先做 demo |
| 独立数据库服务 | PostgreSQL、MySQL | 多用户同时提交任务、权限控制、可靠的历史记录；适合正式平台 |

因此，我们的第一步甚至不需要 SQLite：仍用现有 TLE 文件缓存和配置文件即可。若要保存少量任务历史，SQLite 是比 CSV 更稳妥的过渡方案。将来若平台多人使用、任务较多，再由研发迁移至研究院标准数据库；SQLite 文件不是最终的多人并发方案。

## 内网穿透以后由什么替代？

内网穿透是开发期的临时隧道：让云端平台暂时访问你电脑上 `localhost` 的 FastAPI 服务。它要求电脑开机，地址可能变化，且安全性和稳定性不适合正式运行。

正式部署时，替代方式是：

```text
Vercel 平台后端
  → HTTPS + 鉴权
研究院服务器/云主机上的固定计算服务地址
```

该固定地址可通过域名和 HTTPS 证书访问；服务需要令牌鉴权、日志、超时和限流。若计算服务必须放在研究院内网，则还要由研发/网管提供安全连接方案，例如 VPN、零信任连接器或受控网关。Vercel 云端不能直接访问研究院内网的 `10.x.x.x` 或 `192.168.x.x` 地址。

你本机的 `127.0.0.1:7890` 代理只用于本机访问 SIRIAgent 网站；它不是正式服务之间的连接方案。

## SIRIAgent 里的 “Siri” 是苹果 Siri 吗？

不是。苹果的语音助手名称是 **Siri**；本项目对接的是研究院的 **SIRIAgent Web**，即“空间信息智能服务平台”的自研 Agent 产品，两者没有产品或部署关系。

本轮通过平台公开 bootstrap 信息只能确认应用名为 `SIRIAgent Web`、平台中文名为“空间信息智能服务平台”；其中没有提供 `SIRI` 四个字母的官方英文展开。因此不应自行把它解释成某个缩写，后续可向平台研发询问正式命名含义。

## 建议的推进顺序

1. 向平台研发确认 skill 注册方式，以及正式计算服务放在研究院服务器还是指定云环境。
2. 在本机将现有入口封装为最小 FastAPI 接口，用固定样例验证输入和输出。
3. 研发在测试环境配置平台后端调用该接口；内网穿透仅在必要时做一次临时联调。
4. 用 Docker 部署到确定的长期运行位置，配置 HTTPS、鉴权、TLE 缓存与日志。
5. 平台注册/替换技能，完成“聊天 → 参数追问 → 覆盖窗口 → 选星结果”的端到端验收。

### 现在从哪里开始？

先不要从 Docker、数据库或部署开始。这些是“把服务送上路”的步骤；当前最先要确认的是“平台接不接得到这个服务”。

1. **先向平台研发索要技能注册样例和计算服务部署规范。** 这是唯一外部前置条件。需要拿到现有 `zhejiang_remote_sensing` 的注册位置、调用外部服务的方法、测试环境地址/鉴权规范，以及可用的服务器或云环境。
2. **同时在本工程定义最小接口契约。** 先写一页输入/输出 JSON：输入城市中心点+半径、时间段、卫星编号、分辨率筛选和 MRT/覆盖率目标；输出必须包含覆盖窗口、全池基线、选星结果与未达标原因。此步不改覆盖算法。
3. **拿到规范后做本机 FastAPI 最小 demo。** 只选一个城市、少量光学卫星、自研引擎和一个明确的矩形 Profile，先证明“接口参数 → 现有窗口 → JSON 返回”全链路正确。先不用数据库，也不用内网穿透。
4. **最后才安排临时联调与部署。** 研发若同意，可用内网穿透做一次 Vercel 到本机的临时演示；正式服务则按他们给的服务器/云环境用 Docker 部署。

这样先解决“接口和平台怎么接”，再解决“服务跑在哪里”，不会提前做无用的部署工作。
