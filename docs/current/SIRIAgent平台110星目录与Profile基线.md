# SIRIAgent 平台 110 星目录与 Profile 基线

> 冻结日期：2026-08-31。本文回答三件事：平台目录究竟有哪些字段、哪些数据能直接用于计算、
> 当前 11 城性能处于什么量级。它不是载荷厂家参数证明文件。

## 1. 数据从哪里来

平台卫星清单来自 [SIRIAgent `/api/bootstrap`](https://siri-iota.vercel.app/api/bootstrap)。本机访问
必须经过 mihomo 代理 `http://127.0.0.1:7890`。平台响应还包含城市、技能和前端配置，因此项目
**不保存整份响应**，只白名单提取下列卫星字段：

- NORAD 编号、名称、系列、传感器类别；
- 分辨率、幅宽；
- 平台声称的平均运动、轨道周期和 TLE 状态。

清洗后的冻结目录为 `data/platform/siriagent_110_catalog.json`，平台卫星字段的规范化 SHA-256 为
`abdf20d4da177fcecbd6c9944411a2e1bad661c557f2e09af9d58239697e5649`。这样既能复现实验，也不会把
整份 bootstrap 中与计算无关的前端配置带进仓库。

平台接口没有返回 TLE 两行正文。项目用 NORAD 编号从本地当日 CelesTrak `active.tle` 缓存匹配，
110/110 全部匹配，冻结为 `data/test_data/siriagent_110_snapshot.tle`。其 SHA-256 为
`0357e8eb50ed111f62b00786c1a601279d38f7af3d379fe575e0cdae278d55c5`，TLE 历元范围为
2026-08-19 至 2026-08-30。它是本次可复现快照，不是永不过期的正式运行数据。

## 2. 目录质量审计

| 项目 | 结果 | 计算时怎样处理 |
| --- | ---: | --- |
| 卫星总数 | 110 | 逐颗按 NORAD 建立目录—TLE映射 |
| 可见光 / 高光谱 / 红外 / SAR | 101 / 4 / 2 / 3 | 作为候选池筛选字段 |
| 分辨率和幅宽完整 | 110/110 | 分辨率只筛选；幅宽进入非 SAR 几何 |
| 平台给出轨道周期 | 31/110 | 仅保留作审计，不参与传播 |
| 平台周期与 TLE 推导差值超过 5 分钟 | 27/31 | 一律以 TLE 为准 |
| TLE 推导周期范围 | 91.461～110.338 分钟 | 符合本目录低轨卫星量级 |

平台有些周期值出现 15.9、37.6 分钟等明显不合理量级。覆盖计算不会读取这些字段，而是由 TLE
第 2 行平均运动重新推导周期，并由 SGP4 传播轨道。

平台当前默认口径是“可见光、`resolution_m <= 1.0`”，因此 110 星目录经过筛选后的**实际默认候选池
是 88 颗**。后文性能基准测的是这 88 颗，不应写成“110 颗全部参与几何”。

## 3. 当前 Profile 怎样生成

内置 Profile 名称为 `siriagent_catalog_swath_v1`，与 TLE 源 `siriagent_110_snapshot` 配套。

### 3.1 非 SAR：目录派生矩形

107 颗非 SAR 卫星可以生成可运行的 `Rectangular` 配置：

- 跨轨全宽取平台逐星 `swath_km`；
- 每个传播时刻按当时轨道高度把地面幅宽换算为跨轨视场半角；
- 沿轨半角暂取 60°，明确标记为场景放松假设；
- 分辨率只决定能否入池，不改变足印大小。

这比“把幅宽塞进统一圆锥”更符合推扫条带语义，但仍只能称为**平台目录派生 Profile**：平台没有
提供曝光时长、面阵/推扫模式或真实沿轨有效长度，60°不是载荷厂家值。

### 3.2 SAR：缺参数就阻止，不退回圆锥

平台标为 SAR 的 3 颗卫星是 NORAD 41727、44312、49495。平台只有幅宽，无法唯一反推出近/远
入射角和前/后向限制，因此默认不会让这 3 颗走圆锥近似。只有逐星提供完整原生参数：

```json
{
  "norad_id": 41727,
  "sensor_type": "SAR",
  "sensor_params": [12, 70, 30, 30]
}
```

才能进入几何计算。上面的数字只展示字段顺序，不是 GAOFEN-3 的真实参数。

若请求只选 SAR，缺参会在传播前返回 `invalid_input`；若请求“全部”且未补 SAR 参数，结果会明确列出
被阻止的 SAR 卫星并只计算可运行的非 SAR 候选，不能把结果称为“完整 110 星全池最优”。

## 4. Skill 最小请求

```json
{
  "operation": "coverage_only",
  "city": "宁波",
  "analysis_horizon_h": 8,
  "profile_slug": "siriagent_catalog_swath_v1",
  "catalog_sensor_type": "可见光",
  "max_resolution_m": 1.0
}
```

只指定平台 Profile 时，Skill 自动选择同版本 110 星 TLE 快照。输出会回显候选数、目录哈希、TLE
哈希、Profile 策略版本、每颗星的传感器类别/分辨率/幅宽，以及所有物理假设和被阻止卫星。

## 5. 浙江 11 市性能基准

固定条件：2026-08-30 00:00 UTC 起算 8 小时、5 km 裁剪网格、10 秒覆盖检测、60 秒选星决策、
默认可见光且分辨率不差于 1 m，共 88 颗候选；以下为同一台用户电脑顺序运行一次的结果。

| 衢州 | 444 | 2,797 | 3,316 | 20.759 | 21.645 | 70.439 |

11 市顺序总耗时 286.040 秒，约 4 分 46 秒。单城市总耗时对网格数的一元拟合约为：

```text
总耗时(s) ≈ 0.04523 × 网格数 + 1.679，R² = 0.99968
```

白话说，每增加 100 个 5 km 网格，在这台电脑上约增加 4.5 秒。当前首版“用户一次问一个城市”可
继续使用同步调用；11 市批量任务更适合顺序后台作业或后续加任务队列。峰值来自 Python
`tracemalloc`，只统计 Python 跟踪的内存分配，不等于整个进程的操作系统 RSS。

## 6. 重建、验收与复测

```powershell
$python = (Resolve-Path '.\.venv\Scripts\python.exe').Path # 在当前代码仓库根目录执行

# 在线更新目录时必须走本机代理；更新属于显式基线变更，不能在正式计算中悄悄执行
& $python -B src\prepare_siriagent_catalog.py --active-tle data\tle_cache\active.tle

# 目录/TLE/Profile/Skill 快速端到端验收
& $python -B src\validate_siriagent_catalog.py

# 默认跑绍兴和丽水；加 --all-cities 跑完整 11 市
& $python -B src\benchmark_siriagent_catalog.py --all-cities `
  --output output\siriagent_110_all_cities_benchmark.json
```

在线重建脚本要求目录仍恰好为 110 颗；数量变化会直接报错，提醒开发者审阅平台变化后再更新基线。

## 7. 当前还缺什么

1. 光学/高光谱/红外的真实成像模式和沿轨有效长度；
2. 3 颗 SAR 的原生入射角带与前后向限制；
3. 平台是否强制使用自己的城市边界；
4. 正式 skill 注册样例、`script_id`、工作目录、超时和返回体积限制。

所以现状是：**平台目录、TLE、候选筛选和非 SAR 幅宽链路已经可运行；真实逐星 Profile 只完成了
“目录能证明的部分”，没有把未知参数伪装成已知。**
