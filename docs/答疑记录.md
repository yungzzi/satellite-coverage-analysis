# 答疑记录（FAQ）

> 用途：记录用户问过的问题和白话解答，方便随时回顾、向导师/答辩解释。
> 约定：每次用户提问涉及概念、方法、验证时，在本文件追加一条（日期 + 问题 + 白话解答），并同步提交 git。

## 2026-08-03

### Q1. 仰角为什么和覆盖有关？仰角不是"地上看天上"吗？
仰角确实是目标点处"视线与水平面"的夹角，但卫星看目标的**侧视角 η** 与目标看卫星的**仰角 ε** 是同一个三角形的两个角，几何上一一对应：卫星越偏（η 越大），仰角越低。
"仰角低" = 卫星几乎贴着地平线斜着看过来，视线斜穿大气路径长、图像质量差、易被遮挡。
所以最小仰角是"质量门槛"（默认 10°），不是几何必需。当前默认参数下真正限制覆盖的是视场半角（30°）；分析中高轨或通信链路时，仰角约束才是主角。

### Q2. 覆盖是什么意思？扫到几个点算，还是全部点算？
默认：**至少一个网格代表点被覆盖就算**，同时记录覆盖比例（max_covered_ratio）。
理由：遥感卫星扫过时覆盖带只经过区域的一部分，"全覆盖"对大区域不现实；只看中心点又会漏掉擦边情况。
以后可改阈值（如"覆盖 ≥30% 才算"），参数化即可。

### Q3. 地区是怎么输入的？GeoJSON 哪来的？
程序读 CONFIG["region_geojson"] 指向的 GeoJSON 文件（现在是 data/geo/330000.json=浙江）。
浙江/杭州边界来自阿里 DataV GeoAtlas（geo.datav.aliyun.com，免费公开）。
用户自定义地区三种方式：①提供 GeoJSON 文件；②点+半径；③经纬度 bbox。

### Q4. "浙江近海"这种现成没有的地区怎么处理？
可以用规则生成：海岸线 + 外推距离（如 12/200 海里）生成缓冲区多边形（shapely buffer），
或在 geojson.io 上手绘多边形导出。后续程序会支持"区域生成"功能。

### Q5. 鼠标在地图上圈地的方案可行吗？
可行。推荐先用 geojson.io（零开发，画完导出 GeoJSON 拖进 data/geo/）；
需要集成时可用 Leaflet/Streamlit 写小页面（几十行代码）。对现有管线改动很小。

### Q6. 甘特图不直观，有没有更好的呈现？
甘特图在卫星多时很拥挤。推荐组合：
① 可用卫星数曲线（横轴时间，纵轴"此刻几颗星可覆盖"，为 0 的时段=覆盖空窗/最大间隙）；
② 覆盖时长排名条形图（选星）；
③ 进阶：热力图、地图动画、一键 HTML 报告（图+表+结论）。

### Q7. 怎么验证分析正确性？
① 第三方过境预报对比（Heavens-Above / N2YO 查某颗星对某地的过境时间，与我们对比）——最实用；
② 内部一致性（低轨星窗口 1~4 分钟、GEO 全天覆盖、中高轨约 97 分钟——量级吻合）；
③ 独立软件对比（GMAT / orbitpy 同输入对比）；
④ 拿到历史 TLE 后与 ATK 报告弱对比（ATK 数据仅供参考，不作准）。

### Q9. 用户要不要看代码？

### Q10. 验证做完了吗？结果怎么样？
做完了，结论：**计算是可靠的**。详见 docs/验证报告.md。要点：
① 换一条路重算（独立算法 vs 主程序）：1441 分钟逐分钟 100% 一致；
② 与 N2YO 网站对照：10 天内 31 次过境全部对上，起止时刻平均偏差 6~11 秒（最大 20 秒）；
③ 物理常识：低轨过境时长、轨道周期、GEO 全天覆盖全部合理。
注意：N2YO 的"过境起止"是仰角 0°（地平线）口径，我们的覆盖窗口是仰角≥10° + 视场 30° 口径，比它窄是正常的。

### Q11. 只验证一颗星够吗？多验证了几颗？
不够，所以又补了 4 颗，现在共验证 **5 颗星、4 种轨道类型**：
低轨太阳同步（98°）、低轨高倾角（100°）、低轨低倾角（35°）、中轨（20°、高约 7500 km）、地球同步（GEO）。
结果：4 颗非同步星共 **133 次过境全部与 N2YO 对上**（起止偏差 ≤30 秒，多数 3~11 秒）；
GEO 星在杭州 10 天仰角始终 51°~58°，"全天覆盖"成立。
唯一一条 99%：中轨星的窗口边缘有 1 分钟正好卡在仰角 10.0° 阈值上（两条算法差 0.2°），属边界噪声。
这轮还顺手修了一个 bug：TLE 查找原来用"编号出现在行里"判断，会误匹配到别的星（65563 撞上了另一颗星的纪元小数），已改为按 TLE 标准字段精确匹配，并加了"星名对不上就报警"的检查。

### Q12. coverage_windows 和 coverage_summary 有什么区别？
两个文件是"明细"和"汇总"的关系：
- `coverage_windows.csv` = **窗口明细**：每次"连续覆盖"占一行（卫星、开始、结束、时长、最大覆盖比例）。想查"某颗星某天几点到几点能看"用这个。
- `coverage_summary.csv` = **卫星汇总**：每颗星一行（窗口次数、总覆盖时长、最长窗口、最大空隙、首次/末次覆盖时间）。想排"哪些卫星最有用"用这个。
汇总是从明细聚合出来的：次数=明细行数，总时长=各行时长相加，最大空隙=相邻窗口间隔的最大值。

### Q13. 和网站对比是用这两个文件对比的吗？
**不是直接拿这两个文件去比**，因为口径不同：N2YO 网站给的是"杭州这个点、卫星从地平线升落的可见时间"（单点、仰角≥0°）；这两个 CSV 是"区域覆盖窗口"（区域网格 + 视场 30° + 仰角 10°），不能直接比。
验证脚本做的是：用**和主程序同一套计算逻辑**，单独为杭州点重新算"可见过境"，再和网站逐条对；同时另一条独立算法在浙江全境逐分钟和主程序逻辑对（100% 一致）。所以等于是验证了"这两个 CSV 背后的计算引擎"，而不是文件本身。

### Q14. 覆盖到底是怎么算的？物理和程序？
**物理**：把地区撒成网格代表点（间距约 22 km）。某时刻某颗星"覆盖"该地区 = 至少一个网格点同时满足 ① 在卫星覆盖圆内（星下点为圆心，半径由视场角 30° + 轨道高度决定，高度越高圆越大）② 该点看卫星的仰角 ≥ 10°。把连续满足的时刻合并成窗口。
**程序**：GeoJSON→网格点；TLE→skyfield（内部 SGP4）外推每分钟星下点；haversine 算地心角；几何公式算仰角；几何公式算覆盖圆；两个条件相与；合并连续时刻。
详细的物理推导和逐行说明已经注释进 `src/coverage_analysis.py`（文件头部 + 各几何函数）。

### Q15. 验证算法是什么原理？专业网站验证更有意义吗？
原理：**三条互相独立的路互相对表**。① 主程序逻辑（skyfield）；② 完全绕开 skyfield 的独立算法（raw-sgp4 底层库 + 手写坐标系转换 + 手写几何）；③ N2YO 网站（别人家的实现 + 别人家抓的 TLE）。A 部分让①②在浙江全境逐分钟对比，B 部分让②③在杭州点对比过境。
专业网站验证更有意义的地方：它连 TLE 获取和传播代码都是独立的，能发现我们"内部一致但一起错"的问题；但它的口径是"点可见性"，所以它和内部一致性验证是**互补关系**，不能互相替代。

### Q16. 偏差合理吗？能提交老师吗？需要优化吗？
合理。起止时刻偏差 ≤30 秒（多数 3~11 秒），来源：TLE 更新时差（网站和我们抓的版本可能差一天）、球面 vs 椭球地球模型（约 0.2° 仰角差）、1 分钟时间步长的边界、SGP4 引力常数差异。这在轨道预报领域属于正常精度范围（SGP4 对远期外推本身就有分钟级误差）。
能提交。提交时把口径和局限一起说清（验证的是"可见性"口径；区域覆盖口径由内部双路验证保证）即可，这本身就是严谨做法。
不需要为了验证而优化偏差。可选的两个"锦上添花"：时间步长改成 10 秒（边界更准，计算量 ×6）、地球模型升级 WGS84 椭球。真正要紧的是使用习惯：**TLE 要每天更新**。

### Q17. 怎么手动上网站验证？
1) 打开 https://www.n2yo.com/passes/?s=36110&lat=30.25&lng=120.15&alt=0&days=1 （改 `s=` 后面的编号可换星：36121=YAOGAN-8，42945=YAOGAN-30 02A，65563=YAOGAN-45）
2) 把网页右上角时区切成 UTC（或记下本地时间再换算，北京时间 = UTC+8）
3) 记下某次过境的"开始 / 结束 / 最大仰角"
4) 打开 `output/validation/compare_B_36110.csv` 找同一行：`n2yo_start_utc` 就是我们从网站抓的时间，`ours_start_utc` 是我们算的时间——两者差 ≤30 秒即为一致。
小提醒：网站之后若更新了 TLE，显示时间可能比 CSV 偏移 1 分钟内，属正常。

### Q18. SGP4 和 skyfield 都是计算方法吗？有什么区别？
SGP4 是**算法/数学模型**（一套轨道外推理论，考虑地球扁率、大气阻力等扰动，从 TLE 根数算出卫星任意时刻的位置速度）；skyfield 是**工具库**，它内部就是调用 SGP4（具体是 `sgp4` 这个 Python 包），再帮你把时间换算、坐标系转换、星下点等"配套杂活"封装成现成函数。
比喻：**SGP4 是发动机，skyfield 是整车**——你只管开车（写一行 `sat.at(t).subpoint()` 拿星下点），不用自己研究发动机内部。

### Q19. 输入是轨道参数吗？从轨道参数到覆盖，物理链路是怎样的？
输入是 **TLE（两行轨道根数）**：历元时刻、倾角、升交点赤经、偏心率、近地点幅角、平近点角、平均运动（可换算成轨道周期/半长轴）、BSTAR 阻力系数等。
物理链路（你的理解完全正确）：
轨道根数 →（SGP4 外推，算出任意时刻的位置 = **轨迹**）→（考虑地球自转，转到地固坐标系）→ **星下点**（经纬度+高度）→（纯几何：地心角 / 仰角 / 覆盖圆）→ **覆盖判定**。
"由星下点结合参数直接算覆盖区域"成立，是因为星下点出来后剩下的全是几何；而"程序的好处"在于：164 颗星 × 1440 分钟 × 246 个网格点的几千万次几何判断，程序几秒钟算完还自动出表出图，手算或 ATK 人工操作都做不到。

### Q20. TLE 为什么每天更新？是不是有一个量是变量？
理想二体问题里确实只有**平近点角**随时间变（其他五个根数是常数）——这是课本简化。真实卫星受大气阻力（低轨尤其明显）、地球非球形引力、太阳光压等扰动，**六个根数都会缓慢漂移**；而且 TLE 本身只是地面测站拟合出来的"快照"，不是精确测量。
TLE 越旧，SGP4 外推误差越大：低轨星放几天误差几十公里，放几周几百公里，过境时间会偏几分钟。所以习惯是每天更新（CelesTrak 每天发布新 TLE）。

### Q21. UTC 是什么？
**协调世界时**，全球统一的时间基准（现代版的格林尼治标准时 GMT）。北京时间 = UTC+8。
程序输出全部用 UTC，好处：跨时区不混乱，而且能和网站直接对表（N2YO 页面右上角可以切 UTC 显示）。

### Q22. 什么叫"两行轨道根数"？一颗星的 TLE 各字段分别是什么？
"两行轨道根数"就是 TLE（Two-Line Element），用**两行文本**把一整套轨道参数编码起来（第 0 行是名字，不算）。拿开运一号 OBJECT-B（NORAD 65489）的 TLE 举例：

```
1 65489U 25197B   26214.76178927  .00003409  00000-0  16207-3 0  9993
2 65489  97.4111  40.1999 0013111 197.3448 162.7341 15.19795929 50356
```

第 1 行（元数据 + 时间 + 变化率）：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 行号 | 1 | 第 1 行 |
| 卫星编号 | 65489 | NORAD 编目号（查星都用它） |
| 密级 | U | 公开（Unclassified） |
| 国际标识 | 25197B | 2025 年第 197 次发射的 B 载荷 |
| 历元时刻 | 26214.76178927 | 2026 年第 214.76 天 ≈ 2026-08-02 18:17 UTC，即这套根数"代表"的时刻 |
| 平均运动一阶导数/2 | .00003409 | 每天变化率；>0 说明轨道在衰减（大气阻力） |
| 平均运动二阶导数/6 | 00000-0 | 二阶项，通常为 0 |
| BSTAR 阻力系数 | 16207-3 | 0.16207×10⁻³，大气阻力建模参数 |
| 星历类型 | 0 | 默认 |
| 根数版本号 | 9993 | 第 9993 版（数据更新次数） |
| 校验和 | 3 | 防止抄写/传输错误 |

第 2 行（六个轨道根数，就是你学的那些量）：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 行号 | 2 | 第 2 行 |
| 卫星编号 | 65489 | NORAD 编目号 |
| 倾角 | 97.4111° | 轨道面与赤道面的夹角；>90° 是逆行 → 太阳同步轨道 |
| 升交点赤经 | 40.1999° | 轨道面朝哪个方向（从春分点起算） |
| 偏心率 | 0.0013111 | 接近圆轨道（0=正圆） |
| 近地点幅角 | 197.3448° | 轨道长轴（近地点）指向 |
| 平近点角 | 162.7341° | 卫星此刻在轨道上的位置 |
| 平均运动 | 15.19795929 圈/天 | 每天转 15.2 圈 → 周期 94.75 分钟 |
| 圈数/校验和 | 50356 / 6 | 编目信息 + 防错 |

由平均运动还能推出：周期 = 1440 ÷ 15.19795929 ≈ 94.75 分钟；再用开普勒第三定律 a=(μ(T/2π)²)^(1/3) 得半长轴约 6881 km，减地球半径得**高度约 502 km**——和 SpaceMapper 上公开的轨道数据（497~518 km）对得上，说明字段解码正确。

### Q23. TLE 是谁提供的？是观测得到的吗？
是观测拟合出来的，不是卫星自己上报的。TLE 由**美国太空军的空间监视网（SSN）**用全球地基雷达和光学望远镜跟踪太空目标、拟合出轨道参数生成；官方免费发布渠道是 space-track.org（需注册），CelesTrak 等网站转载（我们的 TLE 就是从 CelesTrak 下载的，你常用的 spacemapper.cn 也是聚合这类公开数据）。
中国也有自己的测轨编目体系，但一般不公开 TLE 格式数据，所以国际通用的是美国这套。

### Q24. 既然考虑摄动，我们的程序就是准确的吗？
要分两层说，不能一口咬定"准确"：
① **程序这一环是准的**：我们已经验证 SGP4 传播 + 几何判定与 N2YO 的 133 次过境全部对上，说明"把 TLE 变成星下点、再变成覆盖窗口"这串计算实现正确。
② **结果的上限取决于 TLE**：TLE 是"快照 + 拟合"，不是精确测量。低轨星在历元附近的位置误差典型就有 1~5 公里，而且会随 TLE 变旧而增长（大气阻力让轨道持续漂移，卫星还可能机动变轨）。SGP4 只能按 TLE 那一个时刻的状态外推，官方也明确不提供误差估计。
所以准确的说法是：**方法标准、实现正确，但预测精度受 TLE 时效限制**——这就是为什么要求每天更新 TLE，也解释了为什么验证里"近 2 天偏差 3~11 秒、第 10 天最大 30 秒"。另外正因为 TLE 是平均根数，不能直接套二体公式，必须用 SGP4 配套使用——我们的程序正是这么做的。
