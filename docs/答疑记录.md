## 2026-08-03

### Q1. 仰角为什么和覆盖有关？仰角不是"地上看天上"吗？
仰角确实是目标点处"视线与水平面"的夹角，但卫星看目标的**侧视角 η** 与目标看卫星的**仰角 ε** 是同一个三角形的两个角，几何上一一对应：卫星越偏（η 越大），仰角越低。
"仰角低" = 卫星几乎贴着地平线斜着看过来，视线斜穿大气路径长、图像质量差、易被遮挡。
所以最小仰角是"质量门槛"（默认 10°），不是几何必需。当前默认参数下真正限制覆盖的是视场半角（30°）；分析中高轨或通信链路时，仰角约束才是主角。

### Q2. 覆盖是什么意思？扫到几个点算，还是全部点算？
默认：**至少一个网格代表点被覆盖就算**，同时记录覆盖比例（max_covered_ratio）。
理由：遥感卫星扫过时覆盖带只经过区域的一部分，"全覆盖"对大区域不现实；只看中心点又会漏掉擦边情况。
以后可改阈值（如"覆盖 ≥30% 才算"），参数化即可。

### Q3. 地区是怎么输入的？GeoJSON 哪来的？
程序读 CONFIG["region_geojson"] 指向的 GeoJSON 文件（现在是 data/geo/330000.json=浙江）。
浙江/杭州边界来自阿里 DataV GeoAtlas（geo.datav.aliyun.com，免费公开）。
用户自定义地区三种方式：①提供 GeoJSON 文件；②点+半径；③经纬度 bbox。

### Q4. "浙江近海"这种现成没有的地区怎么处理？
可以用规则生成：海岸线 + 外推距离（如 12/200 海里）生成缓冲区多边形（shapely buffer），
或在 geojson.io 上手绘多边形导出。后续程序会支持"区域生成"功能。

### Q5. 鼠标在地图上圈地的方案可行吗？
可行。推荐先用 geojson.io（零开发，画完导出 GeoJSON 拖进 data/geo/）；
需要集成时可用 Leaflet/Streamlit 写小页面（几十行代码）。对现有管线改动很小。

### Q6. 甘特图不直观，有没有更好的呈现？
甘特图在卫星多时很拥挤。推荐组合：
① 可用卫星数曲线（横轴时间，纵轴"此刻几颗星可覆盖"，为 0 的时段=覆盖空窗/最大间隙）；
② 覆盖时长排名条形图（选星）；
③ 进阶：热力图、地图动画、一键 HTML 报告（图+表+结论）。

### Q7. 怎么验证分析正确性？
① 第三方过境预报对比（Heavens-Above / N2YO 查某颗星对某地的过境时间，与我们对比）——最实用；
② 内部一致性（低轨星窗口 1~4 分钟、GEO 全天覆盖、中高轨约 97 分钟——量级吻合）；
③ 独立软件对比（GMAT / orbitpy 同输入对比）；
④ 拿到历史 TLE 后与 ATK 报告弱对比（ATK 数据仅供参考，不作准）。

### Q10. 验证做完了吗？结果怎么样？
做完了，结论：**计算是可靠的**。详见 docs/验证报告.md。要点：
① 换一条路重算（独立算法 vs 主程序）：1441 分钟逐分钟 100% 一致；
② 与 N2YO 网站对照：10 天内 31 次过境全部对上，起止时刻平均偏差 6~11 秒（最大 20 秒）；
③ 物理常识：低轨过境时长、轨道周期、GEO 全天覆盖全部合理。
注意：N2YO 的"过境起止"是仰角 0°（地平线）口径，我们的覆盖窗口是仰角≥10° + 视场 30° 口径，比它窄是正常的。

### Q11. 只验证一颗星够吗？多验证了几颗？
不够，所以又补了 4 颗，现在共验证 **5 颗星、4 种轨道类型**：
低轨太阳同步（98°）、低轨高倾角（100°）、低轨低倾角（35°）、中轨（20°、高约 7500 km）、地球同步（GEO）。
结果：4 颗非同步星共 **133 次过境全部与 N2YO 对上**（起止偏差 ≤30 秒，多数 3~11 秒）；
GEO 星在杭州 10 天仰角始终 51°~58°，"全天覆盖"成立。
唯一一条 99%：中轨星的窗口边缘有 1 分钟正好卡在仰角 10.0° 阈值上（两条算法差 0.2°），属边界噪声。
这轮还顺手修了一个 bug：TLE 查找原来用"编号出现在行里"判断，会误匹配到别的星（65563 撞上了另一颗星的纪元小数），已改为按 TLE 标准字段精确匹配，并加了"星名对不上就报警"的检查。

### Q12. coverage_windows 和 coverage_summary 有什么区别？
两个文件是"明细"和"汇总"的关系：
- `coverage_windows.csv` = **窗口明细**：每次"连续覆盖"占一行（卫星、开始、结束、时长、最大覆盖比例）。想查"某颗星某天几点到几点能看"用这个。
- `coverage_summary.csv` = **卫星汇总**：每颗星一行（窗口次数、总覆盖时长、最长窗口、最大空隙、首次/末次覆盖时间）。想排"哪些卫星最有用"用这个。
汇总是从明细聚合出来的：次数=明细行数，总时长=各行时长相加，最大空隙=相邻窗口间隔的最大值。

### Q13. 和网站对比是用这两个文件对比的吗？
**不是直接拿这两个文件去比**，因为口径不同：N2YO 网站给的是"杭州这个点、卫星从地平线升落的可见时间"（单点、仰角≥0°）；这两个 CSV 是"区域覆盖窗口"（区域网格 + 视场 30° + 仰角 10°），不能直接比。
验证脚本做的是：用**和主程序同一套计算逻辑**，单独为杭州点重新算"可见过境"，再和网站逐条对；同时另一条独立算法在浙江全境逐分钟和主程序逻辑对（100% 一致）。所以等于是验证了"这两个 CSV 背后的计算引擎"，而不是文件本身。

### Q14. 覆盖到底是怎么算的？物理和程序？
**物理**：把地区撒成网格代表点（间距约 22 km）。某时刻某颗星"覆盖"该地区 = 至少一个网格点同时满足 ① 在卫星覆盖圆内（星下点为圆心，半径由视场角 30° + 轨道高度决定，高度越高圆越大）② 该点看卫星的仰角 ≥ 10°。把连续满足的时刻合并成窗口。
**程序**：GeoJSON→网格点；TLE→skyfield（内部 SGP4）外推每分钟星下点；haversine 算地心角；几何公式算仰角；几何公式算覆盖圆；两个条件相与；合并连续时刻。
详细的物理推导和逐行说明已经注释进 `src/coverage_analysis.py`（文件头部 + 各几何函数）。

### Q15. 验证算法是什么原理？专业网站验证更有意义吗？
原理：**三条互相独立的路互相对表**。① 主程序逻辑（skyfield）；② 完全绕开 skyfield 的独立算法（raw-sgp4 底层库 + 手写坐标系转换 + 手写几何）；③ N2YO 网站（别人家的实现 + 别人家抓的 TLE）。A 部分让①②在浙江全境逐分钟对比，B 部分让②③在杭州点对比过境。
专业网站验证更有意义的地方：它连 TLE 获取和传播代码都是独立的，能发现我们"内部一致但一起错"的问题；但它的口径是"点可见性"，所以它和内部一致性验证是**互补关系**，不能互相替代。

### Q16. 偏差合理吗？能提交老师吗？需要优化吗？
合理。起止时刻偏差 ≤30 秒（多数 3~11 秒），来源：TLE 更新时差（网站和我们抓的版本可能差一天）、球面 vs 椭球地球模型（约 0.2° 仰角差）、1 分钟时间步长的边界、SGP4 引力常数差异。这在轨道预报领域属于正常精度范围（SGP4 对远期外推本身就有分钟级误差）。
能提交。提交时把口径和局限一起说清（验证的是"可见性"口径；区域覆盖口径由内部双路验证保证）即可，这本身就是严谨做法。
不需要为了验证而优化偏差。可选的两个"锦上添花"：时间步长改成 10 秒（边界更准，计算量 ×6）、地球模型升级 WGS84 椭球。真正要紧的是使用习惯：**TLE 要每天更新**。

### Q17. 怎么手动上网站验证？
1) 打开 https://www.n2yo.com/passes/?s=36110&lat=30.25&lng=120.15&alt=0&days=1 （改 `s=` 后面的编号可换星：36121=YAOGAN-8，42945=YAOGAN-30 02A，65563=YAOGAN-45）
2) 把网页右上角时区切成 UTC（或记下本地时间再换算，北京时间 = UTC+8）
3) 记下某次过境的"开始 / 结束 / 最大仰角"
4) 打开 `output/validation/compare_B_36110.csv` 找同一行：`n2yo_start_utc` 就是我们从网站抓的时间，`ours_start_utc` 是我们算的时间——两者差 ≤30 秒即为一致。
小提醒：网站之后若更新了 TLE，显示时间可能比 CSV 偏移 1 分钟内，属正常。

### Q18. SGP4 和 skyfield 都是计算方法吗？有什么区别？
SGP4 是**算法/数学模型**（一套轨道外推理论，考虑地球扁率、大气阻力等扰动，从 TLE 根数算出卫星任意时刻的位置速度）；skyfield 是**工具库**，它内部就是调用 SGP4（具体是 `sgp4` 这个 Python 包），再帮你把时间换算、坐标系转换、星下点等"配套杂活"封装成现成函数。
比喻：**SGP4 是发动机，skyfield 是整车**——你只管开车（写一行 `sat.at(t).subpoint()` 拿星下点），不用自己研究发动机内部。

### Q19. 输入是轨道参数吗？从轨道参数到覆盖，物理链路是怎样的？
输入是 **TLE（两行轨道根数）**：历元时刻、倾角、升交点赤经、偏心率、近地点幅角、平近点角、平均运动（可换算成轨道周期/半长轴）、BSTAR 阻力系数等。
物理链路（你的理解完全正确）：
轨道根数 →（SGP4 外推，算出任意时刻的位置 = **轨迹**）→（考虑地球自转，转到地固坐标系）→ **星下点**（经纬度+高度）→（纯几何：地心角 / 仰角 / 覆盖圆）→ **覆盖判定**。
"由星下点结合参数直接算覆盖区域"成立，是因为星下点出来后剩下的全是几何；而"程序的好处"在于：164 颗星 × 1440 分钟 × 246 个网格点的几千万次几何判断，程序几秒钟算完还自动出表出图，手算或 ATK 人工操作都做不到。

### Q20. TLE 为什么每天更新？是不是有一个量是变量？
理想二体问题里确实只有**平近点角**随时间变（其他五个根数是常数）——这是课本简化。真实卫星受大气阻力（低轨尤其明显）、地球非球形引力、太阳光压等扰动，**六个根数都会缓慢漂移**；而且 TLE 本身只是地面测站拟合出来的"快照"，不是精确测量。
TLE 越旧，SGP4 外推误差越大：低轨星放几天误差几十公里，放几周几百公里，过境时间会偏几分钟。所以习惯是每天更新（CelesTrak 每天发布新 TLE）。

### Q21. UTC 是什么？
**协调世界时**，全球统一的时间基准（现代版的格林尼治标准时 GMT）。北京时间 = UTC+8。
程序输出全部用 UTC，好处：跨时区不混乱，而且能和网站直接对表（N2YO 页面右上角可以切 UTC 显示）。

### Q22. 什么叫"两行轨道根数"？一颗星的 TLE 各字段分别是什么？
"两行轨道根数"就是 TLE（Two-Line Element），用**两行文本**把一整套轨道参数编码起来（第 0 行是名字，不算）。拿开运一号 OBJECT-B（NORAD 65489）的 TLE 举例：

```
1 65489U 25197B   26214.76178927  .00003409  00000-0  16207-3 0  9993
2 65489  97.4111  40.1999 0013111 197.3448 162.7341 15.19795929 50356
```

第 1 行（元数据 + 时间 + 变化率）：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 行号 | 1 | 第 1 行 |
| 卫星编号 | 65489 | NORAD 编目号（查星都用它） |
| 密级 | U | 公开（Unclassified） |
| 国际标识 | 25197B | 2025 年第 197 次发射的 B 载荷 |
| 历元时刻 | 26214.76178927 | 2026 年第 214.76 天 ≈ 2026-08-02 18:17 UTC，即这套根数"代表"的时刻 |
| 平均运动一阶导数/2 | .00003409 | 每天变化率；>0 说明轨道在衰减（大气阻力） |
| 平均运动二阶导数/6 | 00000-0 | 二阶项，通常为 0 |
| BSTAR 阻力系数 | 16207-3 | 0.16207×10⁻³，大气阻力建模参数 |
| 星历类型 | 0 | 默认 |
| 根数版本号 | 9993 | 第 9993 版（数据更新次数） |
| 校验和 | 3 | 防止抄写/传输错误 |

第 2 行（六个轨道根数，就是你学的那些量）：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| 行号 | 2 | 第 2 行 |
| 卫星编号 | 65489 | NORAD 编目号 |
| 倾角 | 97.4111° | 轨道面与赤道面的夹角；>90° 是逆行 → 太阳同步轨道 |
| 升交点赤经 | 40.1999° | 轨道面朝哪个方向（从春分点起算） |
| 偏心率 | 0.0013111 | 接近圆轨道（0=正圆） |
| 近地点幅角 | 197.3448° | 轨道长轴（近地点）指向 |
| 平近点角 | 162.7341° | 卫星此刻在轨道上的位置 |
| 平均运动 | 15.19795929 圈/天 | 每天转 15.2 圈 → 周期 94.75 分钟 |
| 圈数/校验和 | 50356 / 6 | 编目信息 + 防错 |

由平均运动还能推出：周期 = 1440 ÷ 15.19795929 ≈ 94.75 分钟；再用开普勒第三定律 a=(μ(T/2π)²)^(1/3) 得半长轴约 6881 km，减地球半径得**高度约 502 km**——和 SpaceMapper 上公开的轨道数据（497~518 km）对得上，说明字段解码正确。

### Q23. TLE 是谁提供的？是观测得到的吗？
是观测拟合出来的，不是卫星自己上报的。TLE 由**美国太空军的空间监视网（SSN）**用全球地基雷达和光学望远镜跟踪太空目标、拟合出轨道参数生成；官方免费发布渠道是 space-track.org（需注册），CelesTrak 等网站转载（我们的 TLE 就是从 CelesTrak 下载的，你常用的 spacemapper.cn 也是聚合这类公开数据）。
中国也有自己的测轨编目体系，但一般不公开 TLE 格式数据，所以国际通用的是美国这套。

### Q24. 既然考虑摄动，我们的程序就是准确的吗？
要分两层说，不能一口咬定"准确"：
① **程序这一环是准的**：我们已经验证 SGP4 传播 + 几何判定与 N2YO 的 133 次过境全部对上，说明"把 TLE 变成星下点、再变成覆盖窗口"这串计算实现正确。
② **结果的上限取决于 TLE**：TLE 是"快照 + 拟合"，不是精确测量。低轨星在历元附近的位置误差典型就有 1~5 公里，而且会随 TLE 变旧而增长（大气阻力让轨道持续漂移，卫星还可能机动变轨）。SGP4 只能按 TLE 那一个时刻的状态外推，官方也明确不提供误差估计。
所以准确的说法是：**方法标准、实现正确，但预测精度受 TLE 时效限制**——这就是为什么要求每天更新 TLE，也解释了为什么验证里"近 2 天偏差 3~11 秒、第 10 天最大 30 秒"。另外正因为 TLE 是平均根数，不能直接套二体公式，必须用 SGP4 配套使用——我们的程序正是这么做的。

### Q25. "平均运动一阶导数/2"是啥？为什么它 >0 就说明轨道在衰减？
先拆名字：
- **平均运动 n** = 卫星每天转的圈数（TLE 第 2 行第 7 项，开运一号是 15.198 圈/天）；
- **一阶导数 dn/dt** = 平均运动"每天变化多少"（单位：圈/天²，即每天的圈数变化率）；
- **/2** = TLE 存的是 dn/dt 的一半。原因是平近点角随时间展开时天然带 1/2 系数：
  M(t) = M₀ + n·t + ½(dn/dt)·t² + …，直接把"一半"存进去，程序用时少一步乘法。纯格式约定，没有物理意义。

开运一号的字段值 `.00003409` 表示 (dn/dt)/2 = 0.00003409，所以 **dn/dt = 0.00006818 圈/天²**（正的，很小）。

为什么正数说明轨道在衰减？推理链条：
大气阻力给卫星"刹车"（消耗机械能）→ 轨道半长轴 a 变小（轨道变低）→ 开普勒第三定律 n² = μ/a³，a 变小则 n 变大 → **dn/dt > 0**。
反直觉但正确的点：阻力让卫星"每圈更短"，所以**每天转的圈数反而增加**；低轨卫星线速度其实比高轨更快（要更快才能不掉下来），只是路程短了。

数量级感受：0.000068 圈/天² 意味着一天之后 n 只多 0.000068 圈/天，单看几乎没变；但误差是**按时间平方累积**的：30 天后沿轨相位漂移 ≈ ½×0.000068×30² ≈ 0.031 圈 ≈ 3 分钟。这就是"TLE 越旧越不准、要每天更新"的数学来源。
对照：高轨星（如 GEO 的 YAOGAN-41）几乎没大气阻力，TLE 里该项接近 0；低轨小卫星该项是正的。

### Q26. 验证思路再详细讲讲？两个验证脚本各干什么？参数会影响和网站的误差吗？网站怎么判定覆盖？

**一、验证思路（为什么这么设计）**
核心担忧是"自圆其说"：程序写错了、公式抄错了、数据读错了，都可能输出一个"看起来合理"的错误结果，自己发现不了。所以验证分三层，每层防一种错：
- **A 换一条路重算**（防"实现写错"）：主程序用 skyfield，验证脚本改用底层 sgp4 + 手写坐标转换和几何，两条路在浙江全境逐分钟对比。公式一样但代码完全不同，两边都错成一样的概率极低。
- **B 外部网站对照**（防"我们一致但一起错"）：N2YO 是别人家的实现 + 别人家抓的 TLE，连数据源都独立。A 通过只能证明"我们没写错"，B 通过才能证明"我们和业界标准一致"。
- **C 物理常识**（防"量级离谱"）：过境该多长、GEO 该不该全天覆盖，用直觉兜底。

**二、两个脚本的分工**
- `validate_crosscheck.py`：**单星详查版**（YAOGAN-7），里面装着全部独立算法（raw-sgp4、手写几何、N2YO 解析），还做 A/A2/B/C 全套，逐分钟逐过境打印明细。它既是验证工具，也是"算法仓库"。
- `validate_multisat.py`：**多星批量版**，直接复用上面那套独立算法，对 5 颗星（4 种轨道类型）循环跑 A + B，输出每颗星的对比 CSV 和汇总表。它是日常回归检查用的（换新 TLE 后跑一遍），单星版负责出详细明细。
关系：多星版 = 单星版的"引擎"套上循环。

**三、参数会不会影响和网站的误差？**
设计上**刻意让它们不影响**：
- 与网站的对比（B）用的是**仰角≥0°**的过境起止（和网站同口径）+ **10 秒**时间步长，**完全没用到**视场 30°、仰角 10° 这两个覆盖参数——所以这两个参数不影响和网站的误差；
- **视场半角、最小仰角**只影响"覆盖窗口"本身（它们决定窗口边界在哪），而那部分由 A 的两条独立路径验证，与阈值取多少无关（公式一样，只是门槛高低）；
- **时间步长 1 分钟**影响的是覆盖窗口边界的精度（A2 实测约 ±1 分钟），也不影响与网站的对比（B 用的是 10 秒步长）。
一句话：**参数影响"结果长什么样"，不影响"算法对不对"**；验证的是算法。

**四、网站是怎么判定覆盖的？**
N2YO 只做"单点几何可见性"，没有传感器视场、没有区域网格：
用 SGP4 推卫星相对杭州点的方位/仰角 → 过境起止 = 仰角**穿过 0°（地平线）**的时刻 → 只有**最大仰角 ≥ 选定门槛**（默认显示 10°）的过境才列出来。
所以网站和我们是**两种口径**：网站=点可见性；我们=区域 + 视场 30° + 仰角 10°。这也是为什么对比时要把我们的口径也切成 0°（B 部分），不然差 5 分钟是口径差，不是误差。

### Q27. output/validation 里那些文件都是干嘛的？理解到什么程度够？还继续做吗？
文件分三类，很容易记：
- **对比结果表（成品）**：`compare_A_zhejiang_windows.csv` = A 验证的窗口对比（主程序 vs 独立算法，两行，证明两条路算出同一个窗口）；`compare_B_*.csv` = B 验证的逐过境对比（每行一次过境：`n2yo_*` 列是网站时间，`ours_*` 列是我们算的时间，外加秒级偏差）。`compare_B_n2yo_passes.csv` 是 YAOGAN-7 第一版（旧命名），`compare_B_36110.csv` 是多星版对同一颗星的输出，内容等价。
- **原始页面快照（原料）**：`n2yo_*.html` = N2YO 网页原样下载，脚本从里面解析出过境时间；`fresh_*.tle` / `yaogan7_fresh.tle` = CelesTrak 下载的最新 TLE。这些都能重新下载，所以**没进 git**（.gitignore 排除了），CSV 和脚本才入库。`heavensabove.html` 是当时 Heavens-Above 抓取失败的残留（错误页），可忽略或删除。

理解到什么程度够：掌握**骨架**即可——输入（TLE + 地区 + 时间）→ 程序（SGP4 外推 + 几何判定）→ 输出（覆盖窗口）→ 验证（三条路对照）。某个具体概念卡住就查本文件或直接问，不需要全部细节都懂才能继续。

继续做吗：建议继续。MVP 和验证都已经扎实，下一步做"可用卫星数曲线"（横轴时间、纵轴同时几颗星能覆盖，空窗一眼可见），顺便解决甘特图不直观的问题；之后再做任意地区输入、TLE 自动更新、几千颗星的性能优化。

### Q28. 今天就是 8 月 3 号，算法和网站是不是都在"预测"？
对，而且两者本质上是**同一件事**：都是"从 TLE 出发，用 SGP4 把轨道外推到目标时间段"。
唯一不是"预测"的是 **TLE 本身**——它是过去观测数据拟合出来的快照（美国太空军用雷达/光学望远镜测轨生成）。算法和网站只是把这颗"过去的快照"往未来推。

时间线拆开看：
- TLE 历元 ≈ 8 月 2 日下午（YAOGAN-7 是 15:58 UTC）；
- 我们的分析窗口 = 8 月 3 日 00:00~24:00 UTC（即北京时间 8:00 到次日 8:00）；
- 现在 = 8 月 3 日晚（北京时间）。
所以：分析窗口相对 TLE 历元**全是外推（预测）**；相对"现在"，早上那段是"事后重算"，今晚那段是"预报"——对算法来说没有区别，都是同一个公式。

那验证到底证明了什么？**证明的是"我们的预测实现和业界标准一致"**（算法一致性），而不是"预测一定成真"。要证明"真准"，需要**事后验证**：等时间过去，用更新后的 TLE 回算当时，或拿实测过境记录对照。这可以列为后续步骤（比如 8 月 4 日用新 TLE 回算 8 月 3 日，与今天的预测对比，偏差小说明预测稳定）。

### Q29. 事后验证能做吗？怎么做？
能做，分两个层次：
- **回算稳定性验证（现在就能做）**：等 CelesTrak 发布新 TLE 后（一般每天更新），用新 TLE 回算 8/3 的覆盖窗口，和 8/3 用旧 TLE 的预测对比；偏差小（1 分钟内）说明预测对 TLE 更新不敏感、结果稳定。
- **实测对照（真正的地面真值）**：需要外部实测数据，例如 SatNOGS（全球业余无线电观测网络，公开 API 提供实测过境记录）或光学观测记录。注意无线电可见性和光学可见性口径不同，要做口径转换，属于后续增强。
提醒：现在和网站一致证明的是"实现一致"，不是"一定成真"；事后验证才是证明"准"的那一步。

### Q30. "函数库"是要建三个文件吗？"参数模式"是什么意思？
都不是新概念，是两件简单的事：
- **"函数库" ≠ 三个文件**。它指"把功能拆成一个个能独立调用的函数"，文件怎么分是次要的。我们的实际结构：分析核心仍在 `coverage_analysis.py`（已有）；新增的查询工具 `query_coverage.py` 一个文件里放几个函数——读数据、按时间段查询、导出 Excel、菜单循环。导出只是一个函数，不需要单独文件。
- **交互模式 vs 参数模式**：两者都是"命令行"，区别在于输入是谁给的。
  - 交互模式：运行后程序一步步问你，你一步步答，可反复查询，输 0/q 退出；
  - 参数模式：启动时把参数一次给全（如 `--start 2026-08-03 12:00 --end 14:00 --export xlsx`），程序自动跑完退出，不需要人守着。这是给"别的程序/脚本"用的入口，将来图形界面也是调用同一批函数。
  打个比方：交互模式像人工柜台一问一答，参数模式像填好表格递进去一次办完。

### Q31. Excel 里的"窗口明细"和"卫星汇总"有什么区别？
两张表是"明细"和"汇总"的关系，都按**卫星视角**组织：
- **窗口明细**：每一次"连续覆盖"占一行（卫星、开始、结束、时长、最大覆盖比例）。想查"某颗星某天几点到几点具体能看、那一次覆盖质量如何"用这张。
- **卫星汇总**：每颗卫星占一行（窗口次数、总覆盖时长、最长窗口、最大空隙、首次/末次覆盖时间）。想比较"哪些星最勤快、最值得用"用这张。
关系：汇总 = 明细按卫星聚合——次数=明细行数，总时长=各行时长相加，最大空隙=相邻两次覆盖间隔的最大值。打个比方：汇总像"员工月度考勤总结"（每人一行），明细像"打卡记录"（每次上下班一条）。
它们和"状态表"（时间视角）是互补的：状态表回答"某段时间有谁在"，明细/汇总回答"某颗星表现如何"。

补充：**卫星汇总表从上到下 = 覆盖总时长从多到少**（默认按 total_duration_s 降序）。
并且它的"口径"跟着导出范围走：导出子时段时，只统计该子时段内的窗口（排序也随之变）；
导出整个时段时，统计整个分析时段。这样你看到的每一张表，数字和排名都和它自己覆盖的时间范围一致。

### Q32. Excel 说明页的"生成时间"是什么？UTC 就是时间标准吧？
- **生成时间** = 导出这个 Excel 的时刻（UTC）。它只表示"这份文件是什么时候做的"，和分析内容无关；以后数据更新了，靠它能判断这份文件是新的还是旧的。
- **UTC** 是的，就是国际统一的时间标准（协调世界时，现代版格林尼治标准时 GMT）。北京时间 = UTC+8。例如 "2026-08-04 04:19:27 UTC" = 北京时间 2026-08-04 12:19:27。

### Q33. 覆盖区域取决于什么？考虑地球自转吗？
- **覆盖圆大小**由 视场半角 η 和 轨道高度 h 共同决定：高度越高圆越大、视场角越大圆越大；
  最小仰角决定边缘"算不算有效"（对高轨/大视场，仰角门槛会把覆盖圆边缘再削一圈）。
- **地球自转：考虑了**。SGP4 给的是惯性系里的卫星位置，skyfield 用地球自转（GMST/UT1）
  转到地固系再算星下点，网格点跟着地球转；如果不算自转，星下点会错位、覆盖窗口会完全不对。
  与 N2YO 网站对上（133 次过境）也是地球自转处理正确的间接证据。
- 完整计算链路见 `docs/覆盖计算流程图.md`。

### Q34. 最小仰角是"太近看不清"吗？用角度而不是半径判断，对吗？公式要不要掌握？
- **最小仰角是下限，不是"太近看不清"**：仰角太低（卫星贴地平线、视线斜穿大气）才看不清；
  仰角越高（越接近头顶 90°）反而越好。所以是"太斜/太低看不清"。
- **对，程序用的是地心角 λ，不是地面直线距离**：两者等价——地面距离 ≈ R × λ（弧度），
  1° ≈ 111 km。用角度的原因：球面几何公式天然用角度（haversine 直接给角度），
  而且"视场角→覆盖圆"的推导也是角度链。代码里的"覆盖半径"就是"地心角 λ_max"。
- **公式不需要掌握推导**，但要能看懂参数含义、能判断结果合不合理。公式是程序+验证的职责。
  一个 5 分钟自检例子：低轨 600 km + 视场 30°，扁平近似足印半径 ≈ h·tan(30°) = 600×0.577 ≈ 346 km，
  我们精确公式给 λ_max ≈ 3.2° ≈ 355 km——两者吻合，说明公式合理。

### Q35. 网上开源项目是怎么定义覆盖的？也是固定视场角+最小仰角吗？
是的，全行业（商业软件 + 开源项目）都是同一套定义，只是叫法不同：
- **orbitpy（NASA JPL 开源）**：用户必须给定传感器视场（conical FOV），覆盖 = 目标落在视场内
  且卫星能做观测；
- **STK（行业标准商业软件）**：可见性约束里就有"最小仰角"，文档建议典型值 6~8°；
- **astrora_core（开源）**：明确写"最小仰角：越低覆盖越宽但信号质量越差"；
- **poliastro 教程**：800 km、星下点传感器视场 25°，算可视面积——和我们同款几何；
- **pyaurorax（开源）**：FOV 自带 min_elevation 参数，默认 5°。
结论：**没有哪个工具能只凭轨道数据自动给出覆盖**（轨道数据里没有传感器信息）；
视场角是卫星属性、最小仰角是任务约束，两者都是参数。默认值各不相同（5° / 6~8° / 10°），
我们取视场 30° + 仰角 10° 完全符合惯例，真正要确认的是甲方卫星的真实视场角。

### Q36. 开源项目里的视场角和最小仰角数据从哪来？自己假设的还是查的？
两类来源都有，要分开看：
- **教程/示例代码**：poliastro 例题的 25°、STK 教程里输入的 50°、orbitpy 示例里的锥角、
  以及我们项目的 30°/10°——都是**教学假设值**，用来演示方法，不是从数据库查的。
  这些工具都把"视场角/最小仰角"做成**用户必须填的参数**，不会自动从别处取。
- **真实任务分析**：数值来自**仪器规格书或公开数据库**，例如
  WMO OSCAR（气象/环境卫星仪器库，有真实视场角、刈幅宽度等参数）、
  eoPortal / EO Handbook（对地观测卫星仪器表）、UCS 卫星数据库、制造商官网/论文。
  用这些能查到某颗真实卫星的传感器参数。
- 我们的处境：164 颗 YAOGAN 的公开传感器资料很少（中国遥感星公开信息少），
  所以先用 30° 假设值，配合灵敏度分析（跑 20°/30°/40° 看结果差异），
  等甲方/老师给真实指标再替换。若甲方给的是"刈幅宽度"而不是角度，
  可用 swath ≈ 2·h·tan(η) 换算成视场角。

### Q37. 刈幅宽度是什么？视场角和最小仰角的典型值是多少？
**刈幅宽度（swath width）** = 卫星传感器一次过境时，在地面上拍到的"条带"宽度。
它和视场角一一对应：窄视场 → 窄刈幅（分辨率高但看面小），宽视场 → 宽刈幅（看面大但分辨率低）。
换算（扁平近似）：swath ≈ 2 × 高度 × tan(视场半角)；反过来 视场半角 ≈ atan(刈幅/2 ÷ 高度)。

真实卫星典型值（高度/刈幅 → 视场半角，按公开资料）：
| 卫星/仪器 | 高度 | 刈幅 | 视场半角（约） |
| --- | --- | --- | --- |
| IKONOS（高分详查） | 681 km | 11 km | ≈0.5° |
| Landsat（中分辨率） | 705 km | 185 km | ≈7.5° |
| Sentinel-2 MSI | 786 km | 290 km | ≈10.5° |
| 高分一号 WFV（宽幅普查） | 645 km | 800 km | ≈32° |
| MODIS（宽幅） | 705 km | 2330 km | ≈59° |
| AVHRR（极宽幅） | 833 km | 2900 km | 55.4° |

可见**视场角差异巨大**（0.5° ~ 60°）：我们默认的 30° 属于"宽视场普查"档，
和 GF-1 WFV 这类相机接近；如果甲方卫星其实是窄视场高分星，结果会差很多——
所以灵敏度分析（20°/30°/40°）和问清真实参数都很重要。

最小仰角典型值：通用可见性分析一般取 **5°~10°**（astrora 文档建议 5-10°、
N2YO 默认 10°、STK 地面站建议 6-8°）；特殊任务（如光学监视）可取更高（20°）。
我们默认 10° 在惯例范围内。

### Q38. 为什么说明页"有覆盖卫星数 155"但卫星汇总表只有 40 多行？
原因：两个数字口径不同。
- "有覆盖卫星数 155" 是**整个分析时段**（全天）的全局数字：全时段内至少有一个覆盖窗口的卫星数；
- 卫星汇总表在导出**子时段**时只统计该子时段内有窗口的卫星（口径跟随导出范围），所以行数少。
已修复：说明页现在同时给出两套口径——
"本表范围有覆盖卫星数（=卫星汇总行数）"（跟随导出/查询范围，和汇总表行数一致）
和"整个分析时段有覆盖卫星数"（全局 155）以及"星座总卫星数"（164）。
看表时以"本表范围"为准即可。

### Q41. 命令行参数（--mode 那些）是怎么来的？--config 文件又是什么？
- **命令行参数**：主程序用 Python 自带的 argparse 解析。代码里先 `parser.add_argument("--mode", ...)`
  声明支持的参数，启动时 `args = parser.parse_args()` 拿到用户传的值，再用
  `if args.mode: cfg["region_mode"] = args.mode` 覆盖默认 CONFIG。所以"改输入"不用改任何文件。
- **优先级**：命令行参数 > CONFIG 默认值；没传的参数用 CONFIG 默认。
- **引号**：`--start "2026-08-01 00:00:00"` 必须加引号，因为值里有空格，不加引号会被拆成两个参数。
- **--config 文件路径（还没实现，是提议）**：把常用参数组合存成 JSON 文件（如 `hangzhou_aug.json`），
  运行 `python src/coverage_analysis.py --config hangzhou_aug.json` 即可复用。
  优先级：命令行参数 > 配置文件 > CONFIG 默认。适合"经常用同一组参数"的场景。

### Q51. TOML 文件怎么看？语法简单讲讲
TOML 是给配置文件用的文本格式，一共 5 种写法（用 data/satellite_catalog.toml 举例）：
1. **注释**：`#` 开头的一整行不生效，给人看的；
2. **键 = 值**：`name = "中国遥感系列"`（文字加双引号）、`count = 165`（数字不加）、
   `enabled = true`（是/否）；
3. **数组**：`tags = ["遥感", "低轨"]`（方括号、逗号分隔）；
4. **小节**：`[target]` 下面缩进的键归为一组；
5. **表格列表**：`[[collections]]` 表示"往 collections 列表里加一项"，出现几次就是几项，
   花括号 `{ type = "name_filter", value = "YAOGAN" }` 是一行写完一条小记录。
程序按键名取值；`config.example.toml`（分析配置）和 `satellite_catalog.toml`（收藏夹目录）都是这个语法。

### Q73. 撤销 / 重做（2026-08-05）

  撤销"导入文件"只恢复收藏夹条目，已复制到 user_files 的文件本体不删。

### Q77. 搜索原理 + 冷门星校验 + 星座组成与通信星处理（2026-08-06，讨论待拍板）
- **搜索怎么实现的（白话）**：不是"在网页上找"，而是程序直接向 CelesTrak 的数据接口

### Q84. 各操作联网对照 + 离线可用性最大化（2026-08-06）
- **操作 × 是否需要 CelesTrak 请求**：
  - 创建/改名/删除收藏夹、加入收藏夹（搜索页/星座页）：**零请求**（纯本地文件）；
  - 查看/解析"名字规则"收藏夹：**零请求**（用全集 active.tle 本地匹配）；
  - 查看/解析"星座分组"收藏夹：group/*.tle 有缓存→零请求；无缓存→一次请求，
    失败时**回退全集 active.tle 按名字过滤**（新增）；
  - 查看/解析"编号清单"：优先全集 active.tle；少量缺失才逐个下载，

  - 搜索（名字/编号/国际编号）：需要 records.php（元数据），只能缓存命中或联网；
  - 星座"预览成员数"：需要 gp.php 一次请求。
- **active.tle 能干什么**：它是"全集现役 TLE"，名字规则收藏夹全部用它；
  星座分组现在也能回退到它（按名字特征）；编号清单优先查它。
  **它不能**提供搜索用的档案表（所属/发射日期等元数据在 records.php，不在 TLE 里）。
- **结论**：active.tle 在手时，名字规则夹和绝大多数星座夹都能离线查看/解析；
  只有"搜索"和"星座首次下载"必须联网。清空缓存 + 限流时，能用 active.tle 的
  功能不受影响，搜索会明确提示下载失败。

  名字规则 YAOGAN 164 颗离线秒出；大编号清单 300 条缺失时 0.03 秒返回不下载。

### Q85. 批量 vs 逐颗请求分析 + 数据新鲜度平衡（2026-08-06，待拍板）

### Q91. 为什么星链一万多颗反而有空窗，遥感两百多颗反而没有（2026-08-06）
- **遥感无空窗的原因**：遥感家族里含地球同步/高轨星（GAOFEN-13 01/02、GAOFEN-4、
  YAOGAN-41），相对地面几乎固定、正好在目标上空 → 全天 100% 覆盖，一颗就保证
  任何时刻有覆盖，所以空窗 0 段。
- **星链有空窗的原因**：星链全是约 550km 低轨快飞星，单颗过境仅约 80 秒；一万颗是
  "全球平均密度高"，但对杭州 5km 小圆目标，任意时刻恰好飞到上空且仰角≥10° 的星
  有限（每分钟 4~9 颗），轨道相位分布仍有间隙 → 全天 5 段空窗。
- **本质**：覆盖空窗取决于"任意时刻该目标上空有没有可见卫星"，即轨道几何，
  不是卫星总数。比喻：固定探照灯（GEO）永远照着你；一万个移动探照灯（LEO）
  密度再高也有恰好全没照到你家这个点的时刻。
- **对选星/星座设计的启示**：高轨/同步星提供"保底覆盖"，低轨大星座提供
  "频繁重访"；两者互补。

### Q99. 选星启动：理论依据 + 吉林一号测试文件 + 文献后置（2026-08-06）

  另加"需求"参数（建议三个：最大重访间隔 MRT、平均重访间隔 ART、最少同时可见数 K）。
- 理论依据（白话，用户不看文献）：
  - 选星 = 从卫星池里挑"最少的一组星"满足覆盖需求 → 数学上等价"集合覆盖问题 Set Cover"（NP-hard）；
  - 解法①贪心：每次挑"盖住最多未覆盖需求"的星，秒级完成，理论最坏 ln n 倍（n=需求片数），实际通常接近最优；
  - 解法②整数规划 ILP：每颗星一个 0/1 变量 + "每个需求片至少被选中星覆盖 K 次"约束，求精确最优；
    几百颗星 × 1 天规模可用 scipy.optimize.milp / OR-Tools 求解；
  - 工程策略：贪心先出方案（秒级），小规模用 ILP 求最优对照；两者一致即可交付。
  - 量化指标：MRT（最大空窗）≤ 需求值、ART（平均重访）、K（同时可见数）——"每 30 分钟至少一次"就是 MRT≤30min 的表达。
  - 开源参考：davidmerwin/satellite-placement（覆盖最大化分组）、ESA Ephemerista（星座设计）、
    JSR 2026 MILP 集合（MMRT/MART 公式）。

### Q119. 选星逻辑白话：需求模式 × 目标模式 2×2 组合（2026-08-07）
- 需求模式=及格线（约束）：连续覆盖=每个时间片都达标（0 空窗）；重访=允许最长 X 分钟空窗。
- 目标模式=怎么选（优化目标）：最少颗数=用最少的星达到及格线；给定 N 颗最大化覆盖率=预算 N 颗星，选覆盖时间占比最大的组合（贪心最大边际收益）。
- 四种组合：
  1) 连续+最少颗数：全程无空窗最少几颗（有全程星则 1 颗；无则物理不可行，如实报告）。
  2) 重访+最少颗数：允许空窗≤X 的最少几颗（吉林 58 颗 MRT≤180 → 2 颗）。
  3) 连续+给定 N 颗：不要求一定 0 空窗，用 N 颗尽量覆盖更多时间；结果按连续标准报告满不满足。
  4) 重访+给定 N 颗：同上选星，但按重访标准报告满不满足。
- 关键澄清：目标=给定 N 颗最大化覆盖率时，选星算法与需求模式无关（都是最大化覆盖率）；需求模式只影响"是否达标"的判定与报告。GUI 目前两者都展示，后续可把该提示做进界面。
- 不同 N 的行为：N 越大组合覆盖率单调不减、边际收益递减，趋近全池覆盖率（物理上限）；有全程星时 N=1 即 100%。
- 未满足时选出的星的意义：尽力而为的最优组合（把空窗压到该池子能做到的最小），揭示物理差距（最长空窗 vs 需求），可作备选方案；同一组星在重访口径下可能完全达标。

### Q140. 传感器参数接口再讨论：侧摆复杂度 + 幅宽与视场角的关系（2026-08-09）
- 关键澄清：当前代码的"视场半角 30°"实质是"最大侧摆/离轴角"的简化——默认传感器可朝星下点四周任意方向歪头最多 30°，足印是"可达圆盘"。这正是 STK/Orekit 等专业工具"访问（access）"判据的标准做法（圆锥视场 + 最小仰角）。所以"选星/覆盖窗口"层面的侧摆能力其实已经算进来了，不是漏掉的。
- 幅宽 vs 视场半角：对天底条带两者数学等价（W ≈ 2·h·tan η；球面精确式 tan η = R·sin λ / (r − R·cos λ)，λ = W/(2R)），输入幅宽可换算成半角后走同一套计算。但语义完全不同：真实光学幅宽 10–30 km 对应半角仅约 0.4°–1.2°（700 km 高度），足印变成小圆，覆盖窗口只有几秒~几十秒（"只拍天底、不侧摆"的模型）；现在的 30° 是"能歪头看多远"，不是光学半角。严谨建模需要两个参数：最大侧摆角（决定可达圆盘）+ 幅宽（决定瞬时条带），二者不能互相替代。
- 严格条带级侧摆建模要面对的计算问题：① 每圈侧摆/俯仰指向是决策变量（除非采用"敏捷星总能指向目标"假设，又退化为圆盘）；② 足印变成斜视椭圆/梯形，判覆盖要算真实投影；③ 覆盖窗口变短且"可访问窗口"≠"实际成像时长"（成像驻留只有几秒）；④ 多目标时一颗星一次只能拍一处 → 出现时间冲突，选星从集合覆盖升级为"敏捷对地观测卫星调度问题（AEOSSP，研究级难题）"；⑤ 中国遥感星的幅宽/最大侧摆/机动速度公开资料很少，严格模型的输入本身凑不齐。
- 务实结论（待拍板）：覆盖判据维持"可达圆锥 + 最小仰角"（= 业界 access 判据），不做条带级模拟；改动只做"逐星参数表"（单星 > 星座/家族 > 全局默认），GUI 参数名建议改为"最大侧摆/指向角(°)"，可选提供"幅宽换算"入口。这样算法改动小、计算量不变、窗口语义不变；条带级精化留作后续独立课题。
